# 버터 실제 전투 모션 참조 — 2026-11-03 확인

## 상태와 출처

사용자가 지정한 <https://viewer.dclnslde.com/>에서 **버터 → 인게임 → 기본 / Normal**을
선택해 실제 화면을 재생하고, 같은 뷰어의 Spine 런타임으로 시각별 포즈를 확인했다.
카탈로그 ID는 `battle/butter`, stem은 `Butter`다. `apostles/butter`(로비)와 다르다.

이제 아래 기록은 정지 일러스트나 추측에 근거한 모션 설명이 아니다.
이 문서의 분석은 먼저 진행한 **자료 조사 단계** 기록이다. 그 단계에서는
v34 렌더러나 승인 PNG를 바꾸지 않았고 원본 파일도 프로젝트에 포함하지 않았다.
그 후의 **v35 구현**은 양손/줄·보행·꼬리를 각색하고 원본 손 두 조각을 추가했다.
[현재 적용 상태](BUTTER_CANON.md)와 [포함 에셋/출처](../../assets/butter-2d35/CREDITS.md)를
구분해 읽는다. 원본 Spine 스켈레톤/런타임을 그대로 재생하는 구현은 아니다.

재확인용 URL, 응답 파일 해시, 클립 길이와 관찰 시각은
[butter-motion-reference.json](butter-motion-reference.json)에 저장한다.
외형은 계속 [BUTTER_CANON.md](BUTTER_CANON.md)의 승인 원본이 우선이다.
뷰어의 모델이나 새 후보를 승인 외형으로 자동 승격하지 않는다.

## 실제 확인한 클립

시간은 **원본 클립의 초 단위**이며 우리 게임의 공격 쿨다운을 의미하지 않는다.
소수점은 읽기 편하게 반올림했다.

| 용도 | 뷰어 이름 | 전체 길이 | 확인한 동작 / 주요 구간 |
| --- | --- | ---: | --- |
| 이동 | `Move` | 0.800초 | 양다리가 교대하는 과장된 달리기. 무릎 굽힘, 몸통 상하 이동, 머리·귀·머리카락·꼬리 후속 동작이 함께 존재 |
| 평타 참고 1 | `Attack1_1` | 1.500초 | 손을 모아 장전 → 줄을 얼굴 가까이 당김 → 약 0.667초에 줄이 놓임 → 회수 |
| 평타 참고 2 | `Attack2_1` | 1.500초 | 장전과 발사 후 반동이 다른 공격 변형. 약 0.633초 이벤트 전후에 발사 자세로 전환 |
| 저학년 참고 | `Skill1_1` | 2.333초 | 뜀·공중 장전 → 약 1.100초 발사 전환 → 착지·복귀 |
| 고학년 참고 | `Ultimate1_1` | 3.933초 | 큰 새총 등장 → 크게 줄을 당김 → 약 2.500초 발사 전환 → 반동·복귀 |

이외에 `Die`, `Experience_1`, `Experience_2`, `Groggy`, `Idle`,
`OW1_Attack2_1`, `Spawn`, `Victory`가 있어 총 13개다.
추가 클립은 목록·길이만 확인했으며 이번에 전부 프레임 분석한 것은 아니다.
`Experience_1/2`가 비슷한 길이라고 같은 용도라고 단정하지 않는다.

발사 전후에는 Spine의 `Event` 및 효과음 이벤트도 있다. 자세 변화와 함께
확인했지만, 숫자로 된 이벤트 ID의 실제 피해·투사체 처리 코드는 보지 않았다.
**이벤트 ID를 우리 게임의 피해 로직으로 그대로 복사하지 않는다.**

## 조사 시점의 v34 구현이 어색했던 구체적인 이유

### 1. 걷기는 발끝 두 조각만의 동작이 아니다

원본 `Move`의 0.0 / 0.1 / … / 0.7초 포즈를 같은 배율·원점에서 비교했다.
양다리는 서로 다른 굽힘·교차 상태를 지나고, 귀·머리카락은 몸보다 늦게 따라온다.
당시 v34 렌더러는 상체를 고정하고 부츠 영역을 회전·이동했다.
그래서 진폭만 키워도 원본의 다리 교대나 연결된 몸짓은 생기지 않는다.

**원본을 그대로 베끼는 것도 답은 아니다.** 원본에는 두 발이 그림자에서 떨어지는
뜀 구간이 있다. 사용자는 기존 구현의 부유감을 싫어했다. 우리 게임에는 발의
교대와 회수 순서를 참고하되, 접지 기준이 안정적인 짧은 보폭으로 새로 구성한다.
원본의 머리 눌림·전신 변형을 승인 그림에 무단 적용하지 않는다.

### 2. 사격은 새총 전체를 조금 돌리는 동작이 아니다

`Attack1_1`의 0.300 / 0.600 / 0.633 / 0.667 / 0.700 / 0.850초를 비교했다.
잡는 팔과 당기는 팔의 위치가 각각 달라지고, 줄의 모양이 장전과 발사 사이에서
분명하게 바뀐다. v34의 `weaponAngle`은 잡는 손·새총 조각만 함께 회전시킨다.
왼손의 장전/놓기 그림과 줄의 상태 자체가 없으므로 각도·속도 조정만으로는 부족하다.

당시 렌더러의 일반 공격 발사 비율 `.55`와 원본 평타의 약 `.444`는 다르지만,
**비율 하나만 바꾼다고 장전 동작이 생기는 것은 아니다.** 먼저 손·팔·줄의
필요한 자세를 갖추고, 그 자세의 놓기 시점에 게임 투사체를 맞춰야 한다.
원본 1.5초를 게임 공격 간격에 그대로 강제하지 않는다.

### 3. 꼬리는 중앙 뿌리와 끝부분의 움직임을 분리해야 한다

원본 연결은 `Pelvis_1 → tail_0 → tail_1 → tail_2`다.
`Move`의 8개 샘플에서 뿌리 `tail_0`의 로컬 회전은 동일했고,
중간·끝 관절의 회전은 서로 다르게 변했다. 골반이 움직이므로 뿌리의 **화면 좌표**가
고정된다는 뜻은 아니다. 중앙 골반에 연결된 뿌리를 유지한 채 꼬리 끝이 따라와야 한다.
꼬리 이미지를 통째로 좌우 평행 이동하면 사용자가 지적한 탈착 느낌이 다시 생긴다.

### 4. 방향별 자료와 이동 사격은 별도 제작 문제다

이번에 확인한 `battle/butter / Normal`에는 방향 이름을 가진 네 벌의 클립이나
`WalkShoot` 클립이 없었다. 확인 화면은 주로 정면에 가까운 3/4 방향이다.
사이트 전체에 후면 자료가 없다는 뜻은 아니지만, **상하좌우 전부 확보했다고
보고하면 안 된다.** 원본 `Move`와 공격 클립도 각각 전신 동작이다.

우리 게임은 승인된 네 방향을 각각 유지하면서 보행 하체와 공격 상체를 합성해야 한다.
좌우 반전으로 손잡이를 바꾸거나 전신 공격 그림으로 보행을 덮어쓰면 안 된다.
원본 리그도 일부 이름만으로 해부학을 추정하기 어렵다. 실제로
`hand_1_L_Weapon`은 `Hand_R` 아래에 있고, `Foot_L/Foot_R` 이름과 부모의
좌우 표기가 교차한다. 이름이 아니라 화면·계층·승인된 손잡이를 함께 확인한다.

## 다음 제작에 필요한 2D 구성

승인 PNG를 보존한 별도 후보에서 다음 부위의 **가려진 부분까지 온전한 그림**을
준비한다. 정지 PNG의 반쯤 가려진 조각을 억지로 늘려 대신하지 않는다.

- 고정 얼굴/머리 기준, 앞·뒤 머리카락 및 귀의 제한된 후속 동작.
- 몸통/골반, 서로 독립적인 양다리의 접지·회수·교차 자세.
- 오른팔+새총, 왼팔+당기는 손의 장전/놓기 자세, 별도 새총 줄.
- 골반 중앙에 고정된 꼬리 뿌리와 작은 후속 움직임을 가진 끝부분.
- 고학년용 큰 새총과 줄. 평타 조각 확대만으로 대체하지 않음.

아래·왼쪽·위·오른쪽 각각에서 물리적 오른손/왼손을 유지한다.
머리와 몸통의 비율·색을 바꾸지 않고, 이동 사격 중에도 양발이 교대해야 한다.
시트 전체에 공통 배율·발 기준점·최대 포즈 여백을 쓴다. 조사용 포즈 비교에서
클립별로 화면에 맞춘 배율은 최종 게임 스프라이트 배율로 재사용하지 않는다.

검토 순서는 **네 방향 걷기+평타 이동 사격 → 꼬리/머리 후속 동작 → 스킬**이다.
96px와 160px에서 원본과 후보를 나란히 확인하고, 동작 줄이기 환경의 재생 안내,
실제 재생, 양손/줄의 발사 동기화, 상향 포즈의 잘림까지 확인한 뒤 적용한다.

## 다시 확인하는 방법

1. 뷰어의 캐릭터 선택에서 `버터` 검색, `인게임` 카드, 기본 `Normal` 스킨 선택.
2. 애니메이션 메뉴에서 위 다섯 클립을 선택해 재생한다.
3. 평타는 0.60–0.70초, 저학년은 1.067–1.133초, 고학년은 2.30–2.567초를 비교한다.
4. 기록 JSON의 출처·해시와 달라지면 새 버전으로 재확인한다.
5. 실제 화면을 못 본 작업에서는 이 문서의 관찰 기록과 새 관찰을 구분한다.

클라우드에서는 승인된 네트워크 경로 및 TLS 검증을 유지했다. 브라우저의 CA 신뢰
문제로 직접 로딩이 실패한 요청은 동일 URL을 시스템 CA를 쓰는 `curl`로 받아
브라우저에 전달했다. 로그인·비공개 API·접근 제어 우회는 사용하지 않았다.
