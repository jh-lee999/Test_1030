# v85 — 열린 문 통로와 사라지는 스프라이트 방어

2026-11-06 Asia/Seoul. 신고 시드 `1793961062183`.
제공된 화면에는 캐릭터 그림자/판정 원·바닥·나무상자 등은 있지만 캐릭터와 문 이미지가
보이지 않았다. 사용자의 브라우저 콘솔/기기 정보를 직접 확보하지 않았으므로, 그 기기에서
정확히 어떤 GPU/디코더 오류가 났는지 확정했다고 주장하지 않는다.

공유된 소스 셀 캐시는 OffscreenCanvas→ImageBitmap 전송/해제 경로였다. 이 경로와
무관한 바닥/나무상자는 다른 그리기 방식을 사용한다.85는 전송 수명에 의존하지 않는
CPU-backed DOM Canvas 셀 캐시로 교체한다. 원작 이미지·프레임·크기·발 기준·발사 시점은
변경하지 않는다.24MiB/192개 상한, LRU는 유지하며 컨텍스트 상실/크기0 캐시는 재생성한다.
캐시 생성 실패는 원본 이미지를 직접 그리는 경로로 돌아간다. 과대 글자는 캐시하지 않는다.
`naturalWidth`만 알려졌다고 디코딩 완료로 보지 않는다. 이미지 로드/디코딩/CPU 준비가
끝나기 전에는 캐시를 만들지 않고, 준비 완료 시 해당 이미지의 과거 셀을 무효화한다.
로딩 도중 임시 투명 셀이 캐시에 계속 남는 경로도 차단한다.
이미지 요청 실패는 최대2회 재시도한다. 원작 모션/정지 그림 모두 불러오지 못한 경우에는
플레이어 위치에 버터 표식이 남아 그림자만 보이는 상태로 진행하지 않게 한다.

문은 이미지 판넬만 올리는 대신 연결 지점의 구워진 배경 벽을 바닥 통로로 덮는다.
`doorsFor`/`boundsFor`의 실제 이동 좌표를 공유하고, 네 방향·네 방 크기 모두 방 가장자리까지
이어진다. 통로 바깥쪽은 그늘로 처리한다. 전투 중·미개방 비밀방·잠긴 황금방은 그대로 닫힌다.
미방문 보스 방에는 진입을 허용하면서 닫힌 보스문 그림을 쓰던 표시 불일치도 수정한다.

변경 파일은85 client/renderer/cache/doors뿐이다.84 엔진·생성기·저장 코드는 그대로다.
`butter.dungeon84.v1`의 현재 판을 그대로 이어가며 새 게임/저장 삭제가 필요 없다.
84 루트 원본은 `dungeon84.html`로 보존하고,84 검사 진입 URL만 보관본으로 바꾼다.
84 진단 JSON/옛 소스 해시는 변경하지 않는다. 관련 검사는 URL 변경만 정규화한다.

## 확인 방식

- 단위 검사: 원본 핀/24MiB 제한/전송 API 불능/캐시 할당 실패/컨텍스트 상실/과대 글자/
  문 잠금 표시/네 방향 통로. 신고 시드와24개 추가 시드에서 문 접근점에 놓은 뒤 실제
  이동 tick으로 방을 넘긴다. 생성된 전투 승리가 아니라 명시적 문 접근 fixture다.
- 픽셀 검사: 원본과 새 캐시의 idle/walk/walkShoot/high 및 문에서 실제 불투명 픽셀을 읽는다.
  CPU/GPU의 알파/보간 차이를 허용하되 불투명 면적 차이2% 미만과 제한된 채널 차이를 검사한다.
- 전송 실패 재현은 **고장 주입**이다. 빈 비트맵을 반환하게 만들면 옛 캐시는 캐릭터 픽셀0,
  새 경로는 캐릭터/문 픽셀이 유지되는지 확인한다. 이것을 사용자 브라우저의 자연 재현으로
  바꿔 말하지 않는다. 실제 Canvas 픽셀/캐시 제거·교체 후 표시도 확인한다.
- 신고 시드 실제 브라우저에서 열린 문 앞에 놓고 A키로 걸어서 이동, 화면 확인 및 재시작.
  보관본84→현재85의 진행 상태도 JSON 전체가 같은지 검사한다.
- 기존 전투·상자·증원·액티브·상점·지도·모바일·실패 경로 검사를85에서도 실행한다.
  성능은 다른 무거운 검사가 끝난 뒤 별도 측정하며 원작 해상도는 줄이지 않는다.
